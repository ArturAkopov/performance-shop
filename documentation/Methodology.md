# 1. Терминология и сокращения

| Термин                        | Расшифровка                                                             |
|-------------------------------|-------------------------------------------------------------------------|
| **SLA**                       | Service Level Agreement — соглашение об уровне предоставляемого сервиса |
| **SLO**                       | Service Level Objective — целевой уровень обслуживания                  |
| **VU**                        | Virtual User — виртуальный пользователь                                 |
| **RPS**                       | Requests Per Second — запросов в секунду                                |
| **Пейсинг (Pacing)**          | Время между началом выполнения двух последовательных итераций сценария  |
| **Think Time**                | Время паузы между действиями пользователя внутри сценария               |
| **Scenario-Based**            | Подход, моделирующий реальное поведение пользователя                    |
| **Закрытая модель**           | Фиксированное количество VU, циклически выполняющих сценарий            |
| **1x**                        | Базовый уровень нагрузки, соответствующий пиковому часу (≈0.06 RPS)     |
| **2x**                        | Двукратная нагрузка от пикового часа (≈0.12 RPS)                        |
| **3x**                        | Трёхкратная нагрузка от пикового часа (≈0.18 RPS)                       |
| **Ultimate Thread Group**     | Плагин JMeter для создания сложных многоступенчатых профилей нагрузки   |
| **Throughput Controller**     | Элемент JMeter для процентного распределения нагрузки между сценариями  |
| **Constant Throughput Timer** | Элемент JMeter для ограничения пропускной способности (RPS)             |

# 2. Цели нагрузочного тестирования

1. **Основная цель** — подтвердить или опровергнуть наличие 3-кратного запаса производительности системы Performance
   Shop относительно пикового часа.
2. Проверить стабильность системы при длительной нагрузке (2 часа) на уровнях 1x, 2x, 3x.
3. Подтвердить соответствие системы заявленным SLO (95-й перцентиль) на всех уровнях нагрузки.
4. Выявить узкие места в архитектуре (микросервисы FastAPI + PostgreSQL).
5. Собрать данные для планирования масштабирования и прогнозирования роста нагрузки.

### 4.2.2. Nginx (nginx.conf)

```nginx
events {
    worker_connections 1024;
}

http {
    upstream backend {
        server app1:8000;
        server app2:8000;
        server app3:8000;
    }

    server {
        listen 80;
        server_name localhost;

        location / {
            proxy_pass http://backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            
            proxy_connect_timeout 60s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;

    }
}
```

# 5. Ограничения и допущения

1. НТ не направлено на выявление функциональных дефектов. Все найденные функциональные дефекты фиксируются и отражаются
   в отчёте.
2. Результаты теста анализируются с момента стабилизации нагрузки.
3. Критерии проверяются по данным, полученным за интервал подачи нагрузки длительностью не менее **2 часов** (для тестов
   стабильности).
4. Тестовый стенд не равен продуктивному по мощностям (локальная машина, ограниченные ресурсы).
5. ПО тестового стенда соответствует продуктивному (используются одинаковые Docker-образы).
6. Используемые тестовые данные: 3 предустановленных пользователя (`admin`, `user1`, `user2`) с паролем `admin123`.
7. Для каждого теста выполняется **очистка БД** и **перезапуск контейнеров** для обеспечения чистоты эксперимента.
8. Таймауты Nginx увеличены до 60 секунд для корректной обработки операций с SLO 60 секунд.

# 6. Стратегия тестирования

## 6.1. Условия для проведения НТ

Отсутствие функциональных дефектов на тестовом стенде. Тестирование производительности проводится только после успешного
функционального тестирования.

## 6.2. Виды планируемых тестов

| №     | Вид теста                    | Описание                                                                                                  | Уровни нагрузки | Длительность |
|-------|------------------------------|-----------------------------------------------------------------------------------------------------------|-----------------|--------------|
| **1** | **Тест стабильности при 1x** | Длительный прогон на базовой нагрузке для проверки отсутствия утечек памяти и деградации времени отклика. | 0.06 RPS (1x)   | 2 часа       |
| **2** | **Тест стабильности при 2x** | Длительный прогон на удвоенной нагрузке.                                                                  | 0.12 RPS (2x)   | 2 часа       |
| **3** | **Тест стабильности при 3x** | Длительный прогон на трёхкратной нагрузке.                                                                | 0.18 RPS (3x)   | 2 часа       |

## 6.3. Этапы проведения тестирования

| Этап                       | Описание работ                                                            | Артефакт               |
|----------------------------|---------------------------------------------------------------------------|------------------------|
| **1. Анализ**              | Изучение ТЗ, архитектуры, статистики операций. Определение пикового часа. | Профиль нагрузки       |
| **2. Разработка СНТ**      | Написание скриптов JMeter, параметризация данными, настройка ассертов.    | `performance_shop.jmx` |
| **3. Настройка окружения** | Запуск приложения, настройка мониторинга.                                 | Рабочий стенд          |
| **4. Верификация**         | Одиночный прогон с 1 пользователем (Smoke Test) для отладки.              | Лог отладки            |
| **5. Проведение тестов**   | Запуск тестов стабильности на уровнях 1x, 2x, 3x.                         | `.jtl` файлы           |
| **6. Мониторинг**          | Сбор метрик CPU, RAM, Network через Grafana.                              | Скриншоты дашбордов    |
| **7. Анализ**              | Обработка результатов, построение графиков, сравнение с SLO.              | Отчёт                  |
| **8. Защита**              | Подготовка презентации и финального отчёта.                               | Презентация            |

## 6.4. Модель нагрузки

Используется **закрытая модель** с фиксированным количеством виртуальных пользователей (VU), управляемых через *
*Ultimate Thread Group**.

**Управление нагрузкой осуществляется через:**

- **Ultimate Thread Group** — задаёт количество потоков (VU), время разгона, удержания и остановки.
- **Constant Throughput Timer** — ограничивает пропускную способность для достижения точного значения RPS.
- **Throughput Controller** — распределяет трафик между сценариями в процентном соотношении.
- **Uniform Random Timer** — имитирует think time пользователя (паузы между действиями).

# 7. Формирование профиля нагрузки

## 7.1. Источники данных

- Файл `operations_shop.csv` (статистика операций за июль 2026)

**Период сбора:** 1-30 июля 2026

## 7.2. Определение пикового часа

| Показатель                            | Значение    |
|---------------------------------------|-------------|
| **Пиковый день**                      | 2026-07-05  |
| **Пиковый час**                       | 08:00–08:59 |
| **Количество операций в пиковый час** | 210         |

**Расчёт базового RPS:** 210 / 3600 = 0.058 RPS ≈ **0.06 RPS**

Нагрузка в 0.06 RPS принята как базовый уровень 1x, соответствующий пиковому часу.

## 7.3. Распределение операций

### 7.3.1. Распределение операций в пиковый час

| №         | Операция                   | Кол-во  | Доля     |
|-----------|----------------------------|---------|----------|
| 1         | GET /api/auth/profile      | 28      | 13.3%    |
| 2         | POST /api/auth/login       | 25      | 11.9%    |
| 3         | GET /api/products          | 25      | 11.9%    |
| 4         | GET /api/orders/{id}       | 23      | 11.0%    |
| 5         | POST /api/reports/generate | 22      | 10.5%    |
| 6         | GET /api/reports/sales     | 20      | 9.5%     |
| 7         | GET /api/products/{id}     | 20      | 9.5%     |
| 8         | GET /api/reports/slow      | 17      | 8.1%     |
| 9         | POST /api/orders           | 15      | 7.1%     |
| 10        | GET /api/health            | 15      | 7.1%     |
| **ИТОГО** |                            | **210** | **100%** |

### 7.3.2. Уровни нагрузки (RPS)

| Уровень | Множитель | RPS      | Операций в час | Описание                      |
|---------|-----------|----------|----------------|-------------------------------|
| **1x**  | ×1        | **0.06** | 210            | Базовый уровень = пиковый час |
| **2x**  | ×2        | **0.12** | 420            | Двукратная нагрузка           |
| **3x**  | ×3        | **0.18** | 630            | Трёхкратная нагрузка          |

## 7.4. Сценарии пользователей

| Сценарий                 | Доля | Описание                                                                        |
|--------------------------|------|---------------------------------------------------------------------------------|
| **А: Просмотр товаров**  | 45%  | Авторизация → Профиль → Список товаров → Товар по ID                            |
| **Б: Оформление заказа** | 20%  | Авторизация → Профиль → Список товаров → Товар → Создать заказ → Получить заказ |
| **В: Отчёты**            | 30%  | Авторизация → Отчёт sales → Отчёт slow → Генерация отчёта                       |
| **Г: Healthcheck**       | 5%   | Периодические вызовы /api/health                                                |

```text
Примечание: Процентное распределение сценариев настроено на эмуляцию целостных пользовательских путей (user journeys), 
а не на математически точное воспроизведение частоты вызова каждого отдельного эндпоинта. 
Из-за группировки операций в линейные сценарии (например, наличие шага авторизации в начале каждого пути) итоговое 
распределение вызовов отдельных эндпоинтов в JMeter будет незначительно отличаться от сырой статистики пикового часа (п. 7.3.1). 
Это является консервативной оценкой, так как создает слегка повышенную нагрузку на механизм авторизации, что допустимо и 
даже полезно для проверки общего запаса прочности системы.
```

## 7.5. Настройка Ultimate Thread Group

| Параметр                | 1x              | 2x              | 3x               |
|-------------------------|-----------------|-----------------|------------------|
| **Start Threads Count** | 2               | 2               | 3                |
| **Initial Delay**       | 0 с             | 0 с             | 0 с              |
| **Startup Time**        | 60 с            | 60 с            | 60 с             |
| **Hold Load For**       | 7200 с (2 ч)    | 7200 с (2 ч)    | 7200 с (2 ч)     |
| **Shutdown Time**       | 60 с            | 60 с            | 60 с             |
| **Target Throughput**   | 3.6 samples/min | 7.2 samples/min | 10.8 samples/min |

**Обоснование:** Для достижения низких значений RPS (0.06–0.18) используется **Constant Throughput Timer** в JMeter,
который гарантирует точное количество запросов в минуту (Target throughput = RPS × 60). Количество потоков (VU)
минимально необходимо для поддержания сессий и параллельного выполнения сценариев.

# 10. Критерии успешности

## 10.1. Критерии успешности тестов

| № | Критерий                                  | Способ проверки  |
|---|-------------------------------------------|------------------|
| 1 | Достигнут целевой уровень нагрузки        | JMeter Dashboard |
| 2 | CPU каждого контейнера < 90%              | Grafana          |
| 3 | RAM каждого контейнера < 80%              | Grafana          |
| 4 | Система выдерживает 2 часа без деградации | JMeter Dashboard |
| 5 | Отсутствие утечки памяти                  | Grafana          |
| 6 | Доля ошибок < 1%                          | JMeter Dashboard |
| 7 | SLO выполняется (95-й перцентиль)         | JMeter Dashboard |

## 10.2. SLO (Service Level Objectives)

| Метод | Эндпоинт              | SLO (95 prc) |
|-------|-----------------------|--------------|
| POST  | /api/auth/login       | 150 ms       |
| GET   | /api/auth/profile     | 150 ms       |
| GET   | /api/products         | 150 ms       |
| GET   | /api/products/{id}    | 150 ms       |
| POST  | /api/orders           | 5 s          |
| GET   | /api/orders/{id}      | 5 s          |
| GET   | /api/reports/sales    | 60 s         |
| GET   | /api/reports/slow     | 2 s          |
| POST  | /api/reports/generate | 60 s         |
| GET   | /api/health           | 1 s          |

## 10.3. Критерии успешности завершения НТ

1. Выполнены все запланированные тесты (1x, 2x, 3x).
2. По каждому тесту имеются: время начала/окончания, данные мониторинга, данные времени отклика.
3. Результаты удовлетворяют SLO не менее чем на 95%.
4. Разработан и согласован отчёт о нагрузочном тестировании.
5. 3-кратный запас **подтверждён**, если все критерии выполнены на уровне 3x (0.18 RPS).
