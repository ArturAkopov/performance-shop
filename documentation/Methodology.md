# 1. Терминология и сокращения

| Термин               | Расшифровка                                                                                               |
|----------------------|-----------------------------------------------------------------------------------------------------------|
| **SLA**              | Service Level Agreement — соглашение об уровне предоставляемого сервиса                                   |
| **SLO**              | Service Level Objective — целевой уровень обслуживания (например, время отклика < 1 сек для 95% запросов) |
| **VU**               | Virtual User — виртуальный пользователь                                                                   |
| **RPS**              | Requests Per Second — запросов в секунду                                                                  |
| **Пейсинг (Pacing)** | Время между началом выполнения двух последовательных итераций сценария одним виртуальным пользователем    |
| **Think Time**       | Время паузы между действиями пользователя внутри сценария (имитация размышлений)                          |
| **Scenario-Based**   | Подход, моделирующий реальное поведение пользователя (цепочка действий с паузами)                         |
| **Hit-Based**        | Подход, моделирующий отдельные запросы без привязки к сценарию                                            |
| **Закрытая модель**  | Фиксированное количество VU, циклически выполняющих сценарий                                              |
| **Открытая модель**  | Фиксированная интенсивность запросов (RPS), независимо от ответа системы                                  |
| **1x**               | Базовый уровень нагрузки, соответствующий пиковому часу (1 RPS)                                           |
| **2x**               | Двукратная нагрузка от пикового часа (2 RPS)                                                              |
| **3x**               | Трёхкратная нагрузка от пикового часа (3 RPS)                                                             |
| **FastAPI**          | Веб-фреймворк для Python (асинхронный)                                                                    |
| **Контейнер**        | Docker-контейнер с приложением                                                                            |
| **Telegraf**         | Агент для сбора метрик                                                                                    |
| **Prometheus**       | Система мониторинга и оповещений                                                                          |
| **Grafana**          | Платформа для визуализации данных                                                                         |

# 2. Цели нагрузочного тестирования

1. **Основная цель** — подтвердить или опровергнуть наличие 3-кратного запаса производительности системы Performance
   Shop относительно пикового часа.
2. Проверить стабильность системы при длительной нагрузке (2 часа) на уровнях 1x (1 RPS), 2x (2 RPS), 3x (3 RPS).
3. Подтвердить соответствие системы заявленным SLO (95-й перцентиль) на всех уровнях нагрузки.
4. Выявить узкие места в архитектуре (микросервисы FastAPI + PostgreSQL).
5. Определить максимальную пропускную способность системы.
6. Собрать данные для планирования масштабирования и прогнозирования роста нагрузки.

## 4.2. Конфигурация стенда

### 4.2.1. Docker Compose (docker-compose.yml)

```yaml
version: '3.8'

services:
  telegraf:
    image: telegraf:latest
    container_name: telegraf
    environment:
      - DOCKER_HOST=tcp://host.docker.internal:2375

      - ./telegraf.conf:/etc/telegraf/telegraf.conf:ro
    ports:
      - "9273:9273"

  db:
    image: postgres:15-alpine
    container_name: perf_db
    environment:
      POSTGRES_USER: perf_user
      POSTGRES_PASSWORD: perf_pass
      POSTGRES_DB: perf_shop

      - "5432:5432"

  app1:
    build: .
    container_name: perf_app1
    environment:
      - INSTANCE_ID=app1
      - DATABASE_URL=postgresql://perf_user:perf_pass@db:5432/perf_shop
    ports:
      - "8001:8000"

  app2:
    build: .
    container_name: perf_app2
    environment:
      - INSTANCE_ID=app2
      - DATABASE_URL=postgresql://perf_user:perf_pass@db:5432/perf_shop
    ports:
      - "8002:8000"

  app3:
    build: .
    container_name: perf_app3
    environment:
      - INSTANCE_ID=app3
      - DATABASE_URL=postgresql://perf_user:perf_pass@db:5432/perf_shop
    ports:
      - "8003:8000"

  nginx:
    image: nginx:alpine
    container_name: perf_nginx
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
```

### 4.2.2. Nginx (nginx.conf)

```nginx
events {
    worker_connections 1024;
}

http {
    upstream backend {
        server app1:8000;
        server app2:8000;
        server app3:8000;
    }

    server {
        listen 80;
        server_name localhost;

        location / {
            proxy_pass http://backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            
            proxy_connect_timeout 60s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;
        }
    }
}
```

**Важно:** Таймауты Nginx увеличены до 60 секунд для корректной обработки тяжёлых отчётов с SLO 60 секунд (
`/api/reports/sales`, `/api/reports/generate`).

### 4.2.3. Telegraf (telegraf.conf)


# 5. Ограничения и допущения

1. НТ не направлено на выявление функциональных дефектов. Все найденные функциональные дефекты фиксируются и отражаются
   в отчёте либо заносятся в Jira.
2. Результаты теста анализируются с момента стабилизации нагрузки.
3. Критерии проверяются по данным, полученным за интервал подачи нагрузки длительностью не менее **2 часов** (для тестов
   стабибильности).
4. Тестовый стенд не равен продуктивному по мощностям (локальная машина, ограниченные ресурсы).
5. ПО тестового стенда соответствует продуктивному (используются одинаковые Docker-образы).
6. Настройки тестового и продуктивного стендов должны быть идентичными (с учётом разницы в мощностях).
7. Используемые тестовые данные: 3 предустановленных пользователя (`admin`, `user1`, `user2`) с паролем `admin123`.
8. Для каждого теста выполняется **очистка БД** и **перезапуск контейнеров** для обеспечения чистоты эксперимента.
9. Таймауты Nginx увеличены до 60 секунд для корректной обработки операций с SLO 60 секунд.

# 6. Стратегия тестирования

## 6.1. Условия для проведения НТ

Отсутствие функциональных дефектов на тестовом стенде. Тестирование производительности проводится только после успешного
функционального тестирования.

## 6.2. Виды планируемых тестов

| №     | Вид теста                                            | Описание                                                                                                  | Уровни нагрузки      | Длительность |
|-------|------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|----------------------|--------------|
| **1** | **Тест определения максимальной производительности** | Постепенное увеличение нагрузки до насыщения системы. Определение предела RPS и точки деградации.         | ramp-up от 0 до пика | ~30 мин      |
| **2** | **Тест стабильности при 1x**                         | Длительный прогон на базовой нагрузке для проверки отсутствия утечек памяти и деградации времени отклика. | 1 RPS (1x)           | 2 часа       |
| **3** | **Тест стабильности при 2x**                         | Длительный прогон на удвоенной нагрузке.                                                                  | 2 RPS (2x)           | 2 часа       |
| **4** | **Тест стабильности при 3x**                         | Длительный прогон на трёхкратной нагрузке.                                                                | 3 RPS (3x)           | 2 часа       |

## 6.3. Этапы проведения тестирования

| Этап                       | Описание работ                                                                                         | Артефакт               |
|----------------------------|--------------------------------------------------------------------------------------------------------|------------------------|
| **1. Анализ**              | Изучение ТЗ, архитектуры, статистики операций. Определение пикового часа.                              | Профиль нагрузки       |
| **2. Разработка СНТ**      | Написание скриптов JMeter, параметризация данными, настройка ассертов.                                 | `performance_shop.jmx` |
| **3. Настройка окружения** | Запуск приложения, настройка мониторинга (Telegraf → Prometheus → Grafana).                            | Рабочий стенд          |
| **4. Верификация**         | Одиночный прогон с 1 пользователем (Smoke Test) для отладки.                                           | Лог отладки            |
| **5. Проведение тестов**   | Запуск теста определения максимальной производительности и тестов стабильности на уровнях 1, 2, 3 RPS. | `.jtl` файлы           |
| **6. Мониторинг**          | Сбор метрик CPU, RAM, Network через Grafana.                                                           | Скриншоты дашбордов    |
| **7. Анализ**              | Обработка результатов, построение графиков, сравнение с SLO.                                           | Отчёт                  |
| **8. Защита**              | Подготовка презентации и финального отчёта.                                                            | Презентация            |

## 6.4. Модель нагрузки

Используется **закрытая модель** (фиксированное количество VU) с контролем интенсивности через **Throughput Shaping
Timer** в JMeter.

**Обоснование выбора:**

- Закрытая модель позволяет точно контролировать количество одновременных пользователей
- Throughput Shaping Timer обеспечивает управление RPS на каждом этапе теста
- Сочетание подходов даёт реалистичную нагрузку с контролируемой интенсивностью

# 7. Формирование профиля нагрузки

## 7.1. Источники данных

- Файл `operations_shop.csv` (статистика операций за июль 2026)
- Данные о пользовательской активности из логов приложения

**Период сбора:** 1-30 июля 2026

## 7.2. Определение пикового часа

Пиковый час определяется как час с максимальной интенсивностью операций.

**Результаты анализа:**

| Показатель                            | Значение    |
|---------------------------------------|-------------|
| **Пиковый день**                      | 2026-07-05  |
| **Пиковый час**                       | 13:00–14:00 |
| **Количество операций в пиковый час** | 227         |

**Расчёт базового RPS:** 227 / 3600 = 0.063 RPS ≈ **1 RPS**

Нагрузка в 1 RPS принята как базовый уровень 1x, соответствующий пиковому часу.

## 7.3. Отбор операций для нагрузки

Отбор операций выполняется по трём критериям:

1. **Частота операций** — наиболее часто выполняемые операции.
2. **«Тяжесть» операций** — операции, потребляющие значительные ресурсы (CPU, память, дисковый ввод-вывод).
3. **Бизнес-критичность** — операции, важные для основного функционала системы.

|---------------------------------------|-------------------------------|
| **Think Time (средний)**              | 1 000 мс (0.5–2 с, случайный) |
| **Среднее время выполнения сценария** | 5 секунд (средневзвешенное)   |

### 7.4.2. Сценарии пользователей

#### Сценарий А: Просмотр товаров (~60% пользователей)

|---------------------------|------------------------|--------------------|-----------------|

| **Общее время сценария**  |                        |                    | **≈ 3 секунды** |

#### Сценарий Б: Оформление заказа (~30% пользователей)

| Шаг                       | Действие               | Длительность (ср.) | Кумулятивно    |
|---------------------------|------------------------|--------------------|----------------|
| 1                         | POST /api/auth/login   | 0.15 с             | 0.15 с         |
| 2                         | GET /api/auth/profile  | 0.15 с             | 0.30 с         |
| 3                         | GET /api/products      | 0.15 с             | 0.45 с         |

| 5                         | POST /api/orders       | 1.00 с             | 1.60 с         |

#### Сценарий В: Отчёты (~10% пользователей)

|---------------------------|----------------------------|--------------------|-----------------|

| 4                         | POST /api/reports/generate | 5.00 с             | 11.65 с         |

| **Общее время сценария**  |                            |                    | **≈ 15 секунд** |

### 7.4.3. Средневзвешенное время сценария

```
Среднее время = (60% × 3с) + (30% × 6с) + (10% × 15с) = 1.8 + 1.8 + 1.5 = 5.1 секунды
```

**Принимаем среднее время выполнения сценария = 5 секунд.**

### 7.4.4. Расчёт VU

**Формула:** `VU = (время_выполнения_сценария + think_time + пейсинг) / пейсинг × целевой_RPS`

| Уровень | Целевой RPS | Время выполнения | Пейсинг  | Требуемое VU |
|---------|-------------|------------------|----------|--------------|
| **1x**  | 1           | 5 с              | **10 с** | **~1**       |
| **2x**  | 2           | 5 с              | **10 с** | **~2**       |
| **3x**  | 3           | 5 с              | **10 с** | **~3**       |

> **Примечание:** Пейсинг 10 секунд означает, что каждый VU выполняет итерацию, затем ждёт 10 секунд перед следующим
> запуском. Это обеспечивает равномерную нагрузку при низком RPS.

- Проверить применение в `jmeter.log`: `Max memory = ...`

## 9.3. Диагностика проблем

### 9.3.1. Проблемы генератора (JMeter)

| Признак                                  | Вероятная причина                    | Решение                                                          |
|------------------------------------------|--------------------------------------|------------------------------------------------------------------|
| `java.net.BindException`                 | Кончились исходящие порты            | Увеличить диапазон портов ОС, снизить RPS                        |
| CPU генератора 100%                      | Упёрлись в свой процессор            | Уменьшить количество потоков, использовать распределённый JMeter |
| Время ответа растёт, на сервере спокойно | Проблема на генераторе               | Проверить загрузку генератора                                    |
| OutOfMemoryError в JMeter                | Маленькая куча или слушатели в плане | Увеличить `HEAP`, убрать слушатели из плана                      |

**Правило:** генератор должен быть загружен максимум наполовину.

### 9.3.2. Проблемы приложения

| Признак                          | Вероятная причина                                    |
|----------------------------------|------------------------------------------------------|
| CPU одного контейнера > 90%      | Приложение упирается в процессор                     |
| RAM одного контейнера > 80%      | Возможна утечка памяти                               |
| Время отклика растёт со временем | Утечка памяти или рост очередей в БД                 |
| Ошибки 504 (Gateway Timeout)     | Nginx таймаут (60 с) при выполнении тяжёлых операций |

| №  | Критерий                                                                                 | Способ проверки                             |

## 10.3. Критерии успешности завершения НТ

1. Выполнены все запланированные тесты (п. 6.2).

    - данные времени отклика транзакций (JMeter Dashboard).
3. Полученные результаты удовлетворяют требованиям SLO не менее чем на 95%.
4. Разработан и согласован отчёт о нагрузочном тестировании.
5. 3-кратный запас **подтверждён**, если все критерии выполнены на уровне 3x (3 RPS).
